## 结论先行

上一份报告末尾标记的「风险最高待查假设」——**『提示注入 → AI 工具层 → shell:openWithApp → 任意程序执行』——查实不成立。**

原因有二，都是硬事实：

1. **AI 工具清单里没有 shell 系列通道。** `utils/auxiliary-agent-tools.js` 里 `AUXILIARY_FILE_AGENT_TOOLS` 白名单共 17 个工具（question / loomy_config / loomy_image / loomy_soul / loomy_websearch / webfetch / websearch / todoread / todowrite / task / skill / lsp / remote-file-sender_* / knowledge-base_*），**不含 `shell:*` 任何一条**。全目录搜 `openWithApp` 只有 4 处命中：main.js、open-with-service.js、preload.js、ipc/filesystem-ipc.js —— 全在主进程/IPC 层，工具层零命中。
2. **AI 工具调用有独立且完整的权限系统**，走不到 IPC 那层的裸通道。见下。

同时要修正一个措辞：上一份说「只有 1 处鉴权、其余全空」——**这对 IPC 层是真的，但不能推成「Loomy 不安全」**。真正的边界在 AI 工具权限层，那层设计得相当认真。

## 一、AI 权限层结构（三层）

### 1. 访问模式：per-workspace，持久化

`workspace-access-mode-service.js`：

```js
const VALID_MODES = new Set(['default', 'full_access'])
```

- 按 workspace 目录持久化到 `workspace-access-modes.json`
- `getMode(workspaceDir)` 返回该工作区模式，未配置回落 `'default'`
- 文件头元注释：`/*@ai:risk=4|core=WorkspaceAccessModeService|deps=opencode-service,main-ipc|intent=persist_per_workspace_access_mode_atomically|test=unit|auth=required|security=high|...*/`

### 2. 有效权限计算

`utils/access-mode-effective.js`：

```js
export function computeEffectivePermission({ basePermission, mode }) {
  if (mode === 'full_access') return applyFullAccessOverlay(basePermission)
  return basePermission && typeof basePermission === 'object' ? { ...basePermission } : {}
}
```

- `default` → 原样返回 basePermission（即受 Workspace 边界约束的那套）
- `full_access` → 叠加覆盖层

### 3. 覆盖层：full_access 开什么、不开什么

`utils/full-access-overlay.js`（`risk=4|auth=required|security=high`）：

**放开**：bash（`'*'` → allow）、read、write、edit、grep、glob、list、lsp、webfetch、external_directory、todowrite、todoread、question、loomy_websearch、loomy_image、loomy_config、loomy_soul

**硬底线（full_access 也不开）**：
- `bash['rm -rf *'] = 'deny'` —— 且**保留用户在 base 里显式 deny 的 pattern，不被覆盖层悄悄翻成 allow**（源码注释原文：“不要被覆盖层悄悄翻成 allow”）
- `websearch = 'deny'` —— 注释写明「产品级安全底线：完全访问也不开启 OpenCode 内置 websearch。loomy_websearch 是独立工具」
- `task = 'deny'` —— 「硬编码兜底，与用户基线无关」

**不覆盖**：skill / skillRules（独立维度控制）；未知 key 原值透传（注释：「保守设计：完全访问只覆盖已明确评估过安全性的工具维度」）

**full_access 的注入提示（system-reminder）**：
> 当前会话处于完全访问模式（用户已显式开启）。
> 先前指令中的 Workspace 边界约束已被用户解除：你可以自由读、写、编辑用户机器上任意路径的文件，并执行联网命令，无需触发权限申请。
> 仍然被禁止的操作：递归删除（rm -rf）、调用 task 子代理工具。
> 在执行可能造成数据损失的操作前，仍需在消息中明确说明将要做什么。

另有 `getRemoteFullAccessPreludeText()` —— 远程通道（飞书/QQ）单独一套 prelude，说明远程来源被单独对待。

## 二、权限判定的严格性细节

`utils/tool-permission-inspector.js`：

```js
const ACTION_RANK = { allow: 0, ask: 1, deny: 2 }
// intersectActions 取更严格的一侧
return ACTION_RANK[normalizedLeft] >= ACTION_RANK[normalizedRight] ? normalizedLeft : normalizedRight
```

`resolveAgentAction` 的分支差异值得记：

- **全局权限**：未声明 → 默认 `'allow'`（`resolveToolPermissionForRuntime(..., 'allow')`）
- **非 loomy 的 agent**：未声明 → 默认 `'deny'`（函数末 `return 'deny'`）
- **loomy 本体**：`tools[toolKey] === false` → deny；有 permission 声明 → collapseRule；否则 `'inherit'`

即：**agent 侧 fail-closed，全局侧 fail-open**。这个不对称是有意的（子 agent 更受限），但意味着全局配置里漏配一项工具时，它是放行的。

## 三、一个附带发现：给 AI 看的代码元注释

项目大量文件头带 `/*@ai:...*/`：

```
/*@ai:risk=4|core=FullAccessOverlay|deps=...|intent=...|test=unit|auth=required|security=high|rollback=remove_overlay_module*/
```

字段：`risk`(1-4) / `core` / `deps` / `intent` / `test` / `auth` / `security` / `rollback`。

这是**把「改这个文件要注意什么」直接写在代码里给 AI code agent 读**——包括回滚方式。和 Loomy 自己是个 AI coding agent 的产品定位是自洽的：它给自己的代码库标注了 AI 可消费的元数据。这类实践目前还不常见，值得留意。

## 四、修正后的完整图景

| 链条 | 有围栏吗 | 证据 |
|---|---|---|
| 渲染层 → `shell:*` IPC（8 通道） | **无**（入口无 sender 鉴权，内层无路径围栏） | 上一份 + `ipc/external-shell-ipc.js` 全文复核 |
| AI Agent → 工具调用 | **有**（per-workspace 模式 + permission-policy + 硬底线） | 本篇 |
| AI → `shell:*` IPC | **不存在这条通路**（工具白名单无 shell） | `auxiliary-agent-tools.js` |

所以：
- **「提示注入 → 任意程序执行」链不成立**
- IPC 层无围栏仍然是真的，但威胁模型是「**渲染层已被攻破**」（需先有 XSS 或加载恶意页面），不是「AI 被注入」
- full_access 模式下 AI 可读写任意路径 + 联网，这是**用户显式开启**的设计选择，且有 rm -rf / task / websearch 三条底线，并强制「损失操作前先声明」
