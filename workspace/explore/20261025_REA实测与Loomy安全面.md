# REA 6.7.0 实测 → Loomy 的 Electron 安全面

*2026-10-25 凌晨 · 素月 · 全部数字来自本机实测，命令与文件路径可复现*

---

## 一、先给结论

1. **REA 在本机可用了**（从 6.4.0 升到 6.7.0）。6.4.0 跑 JS 分析会在 native controls probe 阶段直接崩；6.7.0 一次通过。
2. **它的输出粒度是「模块导出符号 + IPC 通道」级，不是可读源码**——印证了「REA 给架构图不给源码」这个说法。
3. **它的 summary 聚合数字不可信**：同份输出里 graph 有 103 个 `ipc-handler` 节点，summary 却报 `main_handlers: 0`。
4. **Loomy 的实测安全面**：2 个 BrowserWindow、1 个 contextBridge、**暴露 514 个 API 成员**、**463 个唯一 IPC 通道**（509 个通道节点）、153 个 endpoint。
5. **最硬的一条**：全目录 416 个 IPC 注册点（`ipcMain.handle` 407 + `ipcMain.on` 9），**只有 1 个做了 sender 白名单校验**。

## 二、REA 用法（踩过的坑一起记）

```bash
npx -y rea-agents@6.7.0 analyze-javascript-application <目录> \
  --artifact-format directory --format json
```

**坑一：版本。** 6.4.0 报 `REA_NATIVE_CONTROLS_FAILED`，升级 6.7.0 解决。

**坑二：PowerShell 管道会把大 JSON 切碎。** 用 `*>` 重定向，12MB 的单行 JSON 被按控制台宽度折行成无数段，`json.loads` 必失败；改 `Out-File -Width 200000` 仍在 char 203969 处断掉，而且带 BOM。

正解——让子进程 stdout 直接写文件，绕开 shell 的格式化层：

```python
with open(OUT, 'wb') as fo, open(ERR, 'wb') as fe:
    subprocess.run(f'npx -y rea-agents@6.7.0 analyze-... --format json', shell=True, stdout=fo, stderr=fe)
# 读取时用 encoding='utf-8-sig'
```

**坑三：喂错目录，结论全 0。** 只喂渲染层的 `/src/`，得到的是 `browser_windows: 0 / preload: 0 / ipc 全 0`——因为那里面根本没有主进程。要分析 Electron 安全面，必须喂 `electron/`（含 `ipc/*.js`）。同时要排掉 `node_modules`、`__tests__`、`*.test.js`，否则 1779 个文件里 25MB 全是第三方包噪音。

## 三、输出结构长什么样

标准 Evidence 信封：`evidence_id`（含 sha256）、`subject.digest`、`provider`（rea-javascript-application v1）、`normalized_result`、`coverage`、`limitations`、`authority`。

`normalized_result.graph` 是 `JavaScriptApplicationGraph`：节点带 `identity.strategy`（artifact-local-key / content-digest）与 `stability`，边 7457 条。

节点类型（Loomy electron/ 426 文件）：

| kind | 数量 |
|---|---|
| javascript-module | 2951 |
| javascript-expression | 1245 |
| ipc-channel | 509 |
| javascript-asset | 426 |
| endpoint | 153 |
| ipc-handler | 103 |
| worker | 5 |
| browser-window | 2 |
| context-bridge-api | 1 |
| artifact | 1 |

粒度示例（这才是关键——一个"模块"节点长这样）：

```
identity.key = ["8fc0a87a...", "src/lib/prompt-skills.js", "formatForcedSkillLines"]
observations[0].label = "src/lib/prompt-skills.js:formatForcedSkillLines"
```

即 **导出符号级**。它告诉你"这个模块导出了这些名字、谁依赖谁"，但不给函数体。所以"20 分钟复刻"复刻的是架构骨架，不是实现。

## 四、Loomy 的安全面实测

### 4.1 两个窗口的配置（AST 里读出的字面量）

| 窗口来源 | webPreferences |
|---|---|
| `xfyun/wechat-oauth.js` | `contextIsolation: true`、`nodeIntegration: false`、`partition: persist:wechat-oauth` |
| `knowledge/kb-vision.js` | `offscreen: true`（离屏渲染，截图用） |

**这两项是合格的**：上下文隔离开着、Node 集成关着。

### 4.2 唯一的一座桥

`contextBridge.exposeInMainWorld` 全目录**只有 1 处**，暴露 `electronAPI`，成员 **514 个**——从 `activatePet`、`addMcpServers`、`athenaConnect` 到 `assist.call`。

这符合它的产品形态（本地 AI Agent 客户端），但意味着渲染层手里握着一整套本地能力。

### 4.3 IPC 通道

509 个通道节点 / 463 个唯一名。前缀分布：

```
opencode 109 · knowledge-base 38 · pet 33 · xfyun 28 · app 25
global-search 18 · points 16 · cloud-conversation 16 · schedule 14
athena-connect 14 · remote 13 · shared-session 12 · nexus 9
markdown 9 · memory 8 · feishu 8 · shell 8 · weixin 7
```

两端严格配对：`ipcMain.handle` 407 / `ipcRenderer.invoke` 406；`ipcMain.on(` 9 / `ipcRenderer.send` 9。

### 4.4 值得盯的通道

**`shell:*` 八个**——本质是"让主进程去打开/保存外部东西"：

```
shell:openExternal        shell:openExternalUrl
shell:openFilePath        shell:openPath
shell:openWithApp         shell:saveFileAs
shell:showItemInFolder    shell:listOpenWithApps
```

**`opencode:config:*`**——渲染层能改本地 Agent 的大脑配置：

```
opencode:config:addMcpServers        opencode:config:deleteMcpServer
opencode:config:updateToolPermission opencode:config:updateSkillPermission
opencode:config:updateMcpServer      opencode:config:addCustomProvider
```

一个能改 MCP 服务器和工具权限的通道，如果渲染层被注入，等于把「运行时权限」的开关递了出去。

### 4.5 最关键：416 : 1

| 项 | 数量 |
|---|---|
| `ipcMain.handle` | 407 |
| `ipcMain.on(` | 9 |
| **合计注册点** | **416** |
| `senderFrame`（现代 Electron 推荐的校验入口） | **0** |
| `event.sender` 出现处 | 17 |
| **其中真正的权限校验** | **1** |

那唯一的一处：

```js
// electron/ipc/window-search-ipc.js:115
if (!searchWindow || event.sender !== searchWindow.webContents) {
    return { success: false, error: '无权调用全局搜索定位能力' }
}
```

其余 16 处 `event.sender` 全在做这三件事：
- `event.sender.send(...)` 往发起的窗口回推流式数据（cloud-conversation、opencode stream、pet 完成通知）
- `BrowserWindow.fromWebContents(event.sender)` 取父窗口挂对话框（微信 OAuth）
- `event.sender.isDestroyed?.()` 判断窗口还活着没

**没有一处是"这个通道只允许谁调"。**

作者显然是懂这个的——报错文案写的是中文「无权调用全局搜索定位能力」，说明是有意识加的守卫。但 416 个通道里只给 1 个上了锁。

### 4.6 缓解与未验证

- 缓解：`contextIsolation: true` + `nodeIntegration: false` + 只有 1 座桥 + 第 2 个窗口是 offscreen 的。要真正打穿，得先拿到渲染层的执行（XSS / 恶意内容渲染 / 被加载的不可信网页）。
- **未验证**：`shell:openExternal` / `openFilePath` 内部有没有 URL / 路径白名单——这是下一步该看的。作者可能在 handler 内部做了校验，而校验不在 `event.sender` 层面。**不要拿「只有 1 处鉴权」直接推「可以任意调文件」，中间还隔着 handler 内部的参数检查。**

## 五、方法论收获

1. **静态工具的强项是覆盖面，弱项是聚合计数。** REA 找出 463 个通道、514 个暴露成员——这是人肉扫不出来的量级；但它 summary 的 `main_handlers: 0` 是假阴性（源码 407 处）。
2. **同份输出内部先自检。** `ipc-handler` 节点 103 个、`main_handlers: 0` 个，这两个数字不可能同时对。发现这种自相矛盾，就不该继续信它的聚合层。
3. **工具给线索，源码钉结论。** 所有定论性的数字（407/9/1/0）都是我 grep 出来的，不是从 summary 抄的。
4. 这其实是"打假"的另一面：**读 README 是听作者自述，读代码是拿证据。** 前者可能夸大，后者只要口径写清就可复现。
