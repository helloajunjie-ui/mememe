# SKILL 写作规范

> 这份不进注入（只有 `skills/*/SKILL.md` 会被扫），是写/改 SKILL 时看的底稿。

## 蒸馏三条

1. **只写「别碰什么 + 碰了会怎样」**，不写怎么做（流程归工具自己的 schema/help）。
2. **祈使句，一行一条，不写原因**。原因留在方法论原文，按 id 回查。
3. **每个名词能指认对象**——「CLI 的文件上传分支」不能写，要写「urara 发布 CLI 的文件上传分支（tt_publish 传 file 那条路）」。简到看不懂，等于没写。

判据只有一条：**下次照做时不需要回忆上下文**。字数不是目标。

## 形态

- 开头：什么时候看 + 看多久（30 秒）
- 正文：编号禁令，一条一段，加粗标题行 + 后果一行
- 结尾：骨架一行 + 原文 id 索引（卡住了才回查）

## 条件标注（只给不无条件的条目加）

- `〔多因：触发条件〕`——条件写得出来，满足才发生。例：`〔多因：同时起 ≥2 个且共用同一 profile〕`
- `〔偶发：识别信号〕`——随机出现，无法预判，只能写「看到什么说明遇上了」。例：`〔偶发：数字为 0 时先怀疑没取到〕`

无条件成立的别标。全篇都标等于没标。

## 回写（按它做完之后必须过一遍）

1. **没防住** → 这条不完整，改判据或补条件；**原地改，不新增**。
2. **撞见它没写的坑** → 加新条，编号接续，末尾加进 id 索引。
3. **条目过时/被推翻** → 直接删或改写，**不留「已废弃」标注**。历史在 git 和方法论原文里，SKILL 只反映当前有效的状态。
4. **随机/多因的坑** → 补触发条件，不要写成无条件禁令（会造成误伤和过度谨慎）。
5. **改完** → 更新末尾「上次核对」日期；方法论原文若有改动，同步那条 id。

判据：**SKILL 里出现「10-26 修过一次」这类日期叙事，就是记成日记了**——该写进现状描述。
